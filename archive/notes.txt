What's left over isn't judgment. It's **sensing** (knowing what B did) and **enforcing** (making B comply), which are interface problems.

### A's duties, sorted

| Duty | Scriptable? | Notes |
|---|---|---|
| Round timer, reminder schedule, 1-min clamp | Fully | Fixed arithmetic |
| Snooze counting, refusing past Zmax | Fully | Counter |
| Status and strategy phase lengths | Fully | Formula from z and x |
| Sitting clock and break trigger | Fully | Accumulator plus threshold |
| Map storage, statuses, crossing out, history | Fully | A state store with an append-only log |
| Map invariants (one doing, one next, both exist) | Fully | Validation on every edit |
| Computing x | Fully | Count nodes that changed to *done* this round, from the log. B doesn't even need to report it |
| Receiving the status report | Fully | Since B keeps the map live, the "report" is just the map diff. It can be shown automatically |
| Understanding B's input | Depends | Trivial with buttons or commands; needs a parser or an LLM for free speech |
| Knowing B actually moved during a break | Partly | Self-report, or a proxy like input idle time or a step counter |
| Making B stop at hard stop | No | A script can announce, lock the screen, or block input, but compliance is ultimately B's |

### What scripting forces you to decide

A human A could improvise through gaps, but a script can't. Writing it would surface these:

- **What counts toward x.** Does clearing a child node count (n7 under n5)? What about a node added and cleared in the same round? Does crossing out a parent cross out its children?
- **Timeouts on B's side.** If B doesn't answer at time-up, is that a decline (hard stop)? If strategy runs out with no D chosen, does N get promoted to D automatically? If commit never comes, does the clock wait or start anyway?
- **Mid-round invariant breaks.** If B crosses out D and doesn't set a new *doing*, does the round pause, end, or keep going with no D?
- **Edits during phases.** Map edits during status and strategy are fine, but should edits during a movement break be blocked, to keep eyes off the task?
- **Sitting reset proof.** With no sensor, the script has to take B's word or use a proxy such as "no keyboard or mouse input for at least Lb."

### The bottom line

A is a state machine: Commit → Work → Snooze prompt → Status → Strategy → Sitting check → (Break) → Commit. It has five inputs from B: *commit(D, N)*, *done*, *snooze*, *decline*, *map edit*. Optionally there's a sixth, *activity signal*, from a sensor. With a button or command interface, A needs no AI at all.
